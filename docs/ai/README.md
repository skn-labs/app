# AI 프롬프트와 대화 계약

SKN의 AI는 모델 기억으로 화장품 상식을 말하는 챗봇이 아니다. 서버가 제공한 개인 데이터와 OpenAI Responses API 안에서 직접 검색한 외부 자료를 분리해 연결하는 기록 파트너다.

## 하나의 채팅, 다섯 가지 맥락

| 모드 | 진입점 | AI가 답할 수 있는 근거 | 답하지 않는 것 |
| --- | --- | --- | --- |
| `GENERAL` | 하단 AI 탭 | 개인 기록, 현재·비교 기준 루틴, 필요할 때 검색한 외부 자료 | 기록에 없는 피부 상태 추론 |
| `PRODUCT` | 제품 상세의 AI 버튼 | 정확한 제품 식별정보, 현재·비교 기준 루틴, 관련 사용 결과, 검색한 외부 자료 | 피부 적합·안전·구매 성공 보장 |
| `RECOMMEND` | 탐색의 다음 제품 찾기 | 서버가 고른 실제 후보 3개, 내 루틴, 과거 결과·패턴, 후보별 검색 자료 | 카탈로그 밖 제품 생성·적합 확률·구매 보장 |
| `PATTERN` | 패턴 상세의 AI 버튼 | 패턴을 지지·반대하는 원본 기록 | 피부 타입·영구 성향 판정 |
| `RESCUE` | 불편 기록 후 이어서 보기 | 비교 기준 이후 변경, 발생 시점, 과거 결과, 서버 제안, 변경 제품의 검색 자료 | 진단·응급도 판정·원인 특정 |

모드는 프롬프트와 서버 맥락만 바꾸며, 화면과 메시지 API는 공통으로 쓴다.

## 프롬프트 조립

```text
shared-v1.txt       전 모드의 개인 사실·검색 출처·안전·표현 경계
+ {mode}-v1.txt     GENERAL / PRODUCT / RECOMMEND / PATTERN / RESCUE 전용 규칙
+ 서버 맥락       정확한 제품 식별정보·현재/비교 기준 루틴·관련 사용 결과·패턴의 실제 ID
+ 사용자 메시지   지금 보낸 문장
```

프롬프트 원문은 [`backend/src/main/resources/prompts`](../../backend/src/main/resources/prompts)에 있다. 대화 이력은 최근 8개 메시지만 제공해 비용과 상관없는 맥락 혼입을 줄인다.

## 추천 입력 규칙

채팅 첫 화면과 대화 중의 추천 입력은 서로 다르게 처리한다.

### 첫 화면

- 프론트엔드가 고정한 예시 3개를 보여준다.
- 개인 기록이 없어도 의미가 통하는 문장만 쓴다.
- 위치: `frontend/src/pages/ChatPages.tsx` 안의 `INITIAL_PROMPTS`.

### 대화 시작 후

- 매 AI 답변이 `suggestedReplies` 1~3개를 같이 반환한다.
- 방금 답한 내용을 반복하지 않고, 사용자가 다음에 궁금할 법한 짧은 1인칭 문장으로 만든다.
- 없는 제품·기록·화면을 있는 것처럼 제안하지 않는다.
- 프론트엔드는 이 배열을 그대로 보여줄 뿐 추가 문장을 만들지 않는다.
- AI 연결 실패 시에도 서버 모드별 직접 답변과 다음 입력을 최대 3개 반환한다. 프론트엔드는 이를 `저장된 내 데이터로 바로 답했어요`로 구분한다.

```json
{
  "answer": "현재 기록에서는 가벼운 마무리에 만족한 경험이 반복됐어요.",
  "suggestedReplies": [
    "아침과 저녁 기록을 나눠서 볼래",
    "반대로 아쉬웠던 기록도 보여줘"
  ],
  "evidenceRefs": ["E-1", "E-2", "E-3"],
  "sourceClassifications": [
    {"url": "https://brand.example/product", "tier": "P1"}
  ]
}
```

OpenAI Responses API의 Structured Outputs로 위 JSON Schema를 강제한다. 제품 비교·추천·Rescue 제안 단계에서는 같은 요청에 `web_search` 도구를 필수로 넣고, 일반·패턴 대화에서는 질문에 외부 사실이 필요할 때 모델이 검색한다. `search_context_size`는 해커톤 계정의 TPM과 모바일 답변 길이를 고려해 `low`를 기본으로 둔다.

서버는 응답을 다시 검증하고 추천 입력은 중복 제거 후 3개·80자 이하만 저장한다. `evidenceRefs`는 서버가 실제로 전달한 ID만 허용하며 모델이 만든 가짜 참조는 버린다. 외부 자료는 OpenAI 응답의 `url_citation` annotation에서 HTTPS URL·제목·문장 위치를 읽는다. 답변 문장에는 클릭 가능한 번호를 넣고, 메시지에는 실제로 인용된 출처만 `S-1`, `S-2` 순서로 저장한다.

외부 출처 선택 순서는 다음과 같다.

1. P1 제품 공식정보: 브랜드·제조사 공식 페이지와 라벨
2. P2 공공기관: 정부·규제기관·공식 공공 DB
3. P3 연구 자료: 원 논문·학술 데이터베이스
4. P4 보조 자료: 판매 페이지·전문 매체·블로그

P4는 식별·사용 맥락 보조로만 쓰고 안전·효능·원인 판단에는 사용하지 않는다. 제조사 표현은 공식 안내일 뿐 효능 입증으로 확대하지 않으며, 원료 연구를 완제품 결과로 확대하지 않는다. 모델이 반환한 출처 분류도 서버가 공공기관·연구 도메인 규칙으로 다시 확인한다.

`answer`는 모바일 채팅에 맞은 Markdown으로 받는다. 첫 문단은 결론, 이후 내용은 최대 4개의 `###` 소제목·목록·강조로 구조화한다. 모바일에서 읽기 어려운 표와 H1, HTML, 직접 생성 링크, 코드 블록은 만들지 않는다. 외부 사실의 링크는 모델 텍스트가 아니라 API `url_citation`에서 서버가 삽입한다. 프론트엔드는 raw HTML을 허용하지 않는 Markdown 렌더러를 사용한다.

사용자가 별도로 AI 대화를 시작하지 않은 메모 원문은 공급자에게 보내지 않는다. 사용자가 AI 대화를 시작하면 질문과 관련된 사용 결과 원문·평가·태그·불편 여부·실제 사용 일치 여부·기록 시각만 제한해서 보낸다. 관련 없는 기록과 업로드 원문은 보내지 않는다.

## Rescue의 역할 분리

```text
사용자 불편 기록
→ 서버의 안전 확인
→ AI가 필요한 추가 정보를 한 번에 하나씩 질문
→ 서버가 비교 기준 이후 변경과 확인 순서를 계산
→ AI가 지지·반대·정보 부족을 설명
→ 사용자가 버튼으로 승인
→ 서버가 새 루틴과 독립된 7일 사용 경험 생성
```

심하거나 빠르게 악화된다는 사용자 표현이 확인되면 서버가 제품 순위와 루틴 제안을 차단한다. AI는 이 결정을 뒤집지 않는다.

## 모델·비용·실패 정책

- 기본 모델: `gpt-5.6-terra`
- reasoning effort: `low`
- 최대 출력: 1,800 tokens. 검색·추론 뒤 구조화 JSON이 잘리지 않게 확보한 예산이며, 사용자에게 보이는 답변 길이는 schema와 프롬프트로 별도 제한한다.
- web search: Responses API `web_search`, 제품·추천·Rescue 판단 단계는 `tool_choice: required`
- source include: `web_search_call.action.sources`
- 재시도: 429·5xx·timeout에만 1회
- 저장: OpenAI `store: false`
- 실패: 사용자 메시지를 먼저 DB에 저장한 뒤 일반은 현재 루틴·최근 결과, 제품은 식별정보·보유 여부·연결 기록, 추천은 카탈로그 후보, 패턴은 반복 근거, Rescue는 변경점·서버 계획으로 직접 답한다. 일반 장애 문구만 사용자 답변으로 저장하지 않는다.

Luna 하나로 일반 대화와 검색 대화를 운영한다. 모델 전환 분기는 두지 않고, 서버의 근거 검증과 실패 시 직접 응답으로 신뢰성과 가용성을 보완한다. 최신 가격과 모델은 [OpenAI API 가격](https://developers.openai.com/api/docs/pricing)에서 확인한다.

## 비밀값

`OPENAI_API_KEY`는 루트 `.env`에만 두고 Spring 서버가 읽는다. 프론트엔드 번들·Git·로그에는 포함하지 않는다.
