# 협업과 구현 흐름

SKN은 화면이나 계층이 아니라 사용자 경험의 수직 흐름 단위로 완성한다. 현재 요청과 작업 트리를 먼저 보고, 관련 요구사항·제품 규칙·OpenAPI·데이터 모델을 같은 기준으로 사용한다.

## 작업 시작

1. `git status`로 다른 세션의 변경을 확인한다.
2. 관련 기능 요구사항과 제품 경계를 읽는다.
3. 실제 `frontend/src`, `backend/src`와 테스트에서 현재 동작을 확인한다.
4. API·데이터·AI 의미가 바뀌는지 판단해 함께 갱신할 계약을 정한다.

GitHub Issues와 Projects는 작업 이력이며 기능명세 원본이 아니다. Figma는 시각 근거지만 서버 상태 전이와 데이터 의미를 결정하지 않는다.

## 구현 단위

한 변경은 가능한 한 아래 흐름을 끝까지 책임진다.

```text
사용자 행동 → 화면 상태 → API → 도메인 검증 → SQLite → 응답 → 다음 행동
```

- 프론트엔드와 백엔드를 따로 완료했다고 보지 않는다.
- 정상 흐름뿐 아니라 로딩, 빈 상태, 권한 오류, 중복 제출, AI 실패와 재시도를 포함한다.
- 사용자가 승인하기 전에는 AI 제안이 루틴이나 개인 사실을 바꾸지 않는다.
- 다른 사용자의 ID를 넣은 요청과 삭제·재시도 뒤 참조 무결성을 확인한다.

## 여러 세션이 같은 작업 트리를 쓸 때

- 기존 수정과 미추적 파일은 다른 세션의 작업으로 간주하고 보존한다.
- 관련 없는 파일을 되돌리거나 브랜치를 강제로 전환하지 않는다.
- 겹치는 파일은 현재 diff를 읽고 최소 범위로 수정한다.
- 사용자가 전체 커밋을 명시하지 않았다면 내가 만든 변경만 커밋한다.
- push 전 최신 상태, 테스트 결과와 비밀값·DB·백업 파일 포함 여부를 다시 확인한다.

## 계약 결합

| 변경 | 같은 변경에서 확인할 것 |
| --- | --- |
| API 요청·응답 | OpenAPI, Java 모델, 프론트 타입, 계약 테스트 |
| 테이블·컬럼·제약 | `schema.sql`, DBML, 데이터 문서, 새 운영 migration |
| AI 모드·근거 | 제품 규칙, prompt, schema 검증, fallback |
| 주요 화면 흐름 | 기능 요구사항, 내비게이션 모델, 접근성·상태 테스트 |
| 배포·운영 | 일관 백업, 롤백, 내부·외부 health |

## 완료 기준

- 관련 자동화 테스트와 빌드가 통과한다.
- SQLite FK가 모든 연결에서 켜지고 외래키·무결성 검사가 통과한다.
- 외부 AI·스토리지 호출이 DB 쓰기 트랜잭션 밖에서 실행된다.
- 로그, fixture와 커밋에 비밀값이나 실제 사용자 기록이 없다.
- 관련 요구사항과 계약이 현재 구현을 정확히 설명한다.
- 핵심 경험 순환의 이전 단계와 다음 단계가 실제 데이터로 이어진다.
